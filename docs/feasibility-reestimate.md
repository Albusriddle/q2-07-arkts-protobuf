# Q2-07 可行性重估（资源可得版）

> 重估日期：2026-10-29 ｜ 基线：主报告 v2.2、R6、W0 证据包
> 重估前提（用户 2026-10-29 明确）：V0–V6、W0-L、W0-P、W0-A 所需资源均可获得/可解决，**不再视作 block**。
> 结论性质：资源可得性重估，不构成对 1.5×/700 ms 的承诺。

## 0. 重估结论

### 0.1 一句话

**资源不再是阻断项；项目从 W0 的“暂不投标（A）”调整为“有条件可投（B+）”。** 但“可投”不等于“能承诺 4.29×/700 ms”：真正的硬约束还剩三个——**ArkTS 对象语义、700 ms 的物理地板、20 周工期**。按“API 级兼容 + P3-batch 优先 + 热点消息 P4”的收缩方案，项目可做；按“值语义完全零改动 + 17 周 + 全量 P4”的原方案，仍不建议。

### 0.2 重估评分

| 维度 | 权重 | 原 v2.0 | 资源重估后 | 说明 |
|---|---:|---:|---:|---|
| 技术原理可行性 | 25% | 4.5 | **4.2** | C++/NAPI/P3-batch 可行；ArkTS 值语义不可完全复刻，降 0.3 |
| 指标可达性 | 25% | 3.0 | **3.0** | 1.5× 可争；700 ms 仍是条件目标，资源不改变物理 |
| 工程实施可行性 | 15% | 4.0 | **3.2** | 资源可得，但 NAPI/性能调试/兼容层工作量大；AI 不能替代真机调试 |
| 资源与物料 | 10% | 5.0 | **4.5** | 板/手机/工具/经费/授权可解决；仍要采购/审批时间 |
| 进度可行性 | 10% | 4.0 | **2.8** | 20 周 base；17 周是 best case，不是承诺 |
| 验收与合规 | 10% | 3.5 | **3.5** | 学校项目、无客户；验收仍看官方数据/口径 |
| 团队与组织 | 5% | 4.0 | **3.8** | 俱乐部+导师+AI；bus factor 仍 1–2 |
| **加权总分** | 100% | **3.93** | **约 3.55（B-，有条件可投）** | 资源加分被技术/工期风险抵消 |

> 评分是专家判断，不是测量结果。3.55 的含义是“可以立项做，但不能按原指标硬承诺”；不是“已经达标”。

### 0.3 决策

| 选项 | 结论 | 条件 |
|---|---|---|
| **A. 不投/改题** | 不推荐 | 只有在“验收方要求值语义完全零改动”或“必须 17 周内完成”时才成立 |
| **B. 有条件投标（推荐）** | **推荐** | API 级兼容 + P3-batch 优先 + 热点消息 P4 + 20 周 + 1.5× 必达/700 ms 目标 |
| C. 社区标准件 | 暂不作为目标 | 先完成 B；有 2–3 个采用者再谈 |
| D. 商业组件 | 不做 | 本项目是大学生揭榜项目，无客户/无商业 KPI，学校经费支持即可 |

## 1. 重估口径：把“资源”与“技术”分开

W0 的 9 个 `BLOCKED` 主要是“缺设备/缺数据/缺书面材料”，不是“技术被证伪”。按用户口径，这些资源均可获得，因此重分类为 **RESOURCE-GATED（资源可得，待到位）**，不再作为 no-go。重估只保留以下四类硬风险：

| 类别 | 是否资源问题 | 是否可通过资源解决 | 重估后的处理 |
|---|---|---|---|
| 板卡/手机/工具链/软件 | 是 | 是（采购/借用/安装） | 不视作 block；进 W0–W2 采购/安装计划 |
| 开源代码/schema/数据 | 是 | 是（下载/AI 生成/自写） | 不视作 block；但必须用“现网版本+真实热点”做最终验证 |
| 法律授权/学校经费 | 是 | 是（已授权/有经费） | 不视作 block；保留书面授权文件 |
| ArkTS 值语义 | **否** | **不能靠资源解决** | 降级为“API 级兼容”，值语义差异书面接受 |
| 700 ms 物理地板 | **否** | **不能靠资源解决** | 1.5× 必达；700 ms 目标/条件 |
| 20 周工期 | 部分 | 资源可缩短采购，但不能压缩调试 | 20 周 base；17 周只作 best case |
| 兼容性/安全正确性 | 部分 | 资源可买工具，但不能买正确性 | 用测试/差分/fuzz 换信心，不承诺零缺陷 |

## 2. 逐项重估

### 2.1 V0 平台：从 BLOCKED 改为“可解决，2–4 周到位”

**你的假设**：板子后面买，其余能解决。

**重估**：

- 采购/借用 RK3568 或同档 OpenHarmony 板：1–2 周；备板 + Android 对照机：另 1 周。
- 安装 DevEco Studio + SDK/NDK + `hvigorw`/`hdc`：3–5 天（首次）。
- 目标代际建议：**优先 API 18 + NAPI-only**（保守、少 ANI 变量）；如果发榜方/验收设备是 API 23/ArkTS 1.2，则选 **API 23 + 1.1/1.2 混合 + NAPI interop**，ANI 只在强制要求时做（+15–25 人日）。
- AOT：不作为必达依赖；如果 RK3568/应用市场不支持 AOT，就按“无 AOT”重算 materializer 预算，不能把 0.45 s 建立在拿不到的 AOT 上。

**剩余风险**：采购延迟、板子变砖、签名/profile 不匹配。**对策**：备板、镜像备份、W0 先装空 HAP + NAPI `.so`。**结论：不是 block，是 2–4 周的前置工程。**

### 2.2 V1 H/k：从 BLOCKED 改为“可测，2–3 天”

**你的假设**：Android 手机能借，工程和数据 AI 能生成。

**重估**：

- H（OH/Android 同 workload 比）和 k（同设备 C++ vs Java 效率比）可以在 2–3 天内粗测；不需要完整 P4。
- 工程：一个 C++ decoder + NAPI/JNI 两套最小封装；AI 可生成骨架，但**JNI/NAPI 调试仍需人工**。
- 数据：AI 生成 100 MB 合成数据可以跑通脚本，但**最终结论必须用真实/官方数据复核**；合成数据只能证明“脚本可跑”，不能证明“业务可外推”。

**剩余风险**：借不到同档位手机、Android ART 状态不可控、数据分布不真实。**对策**：记录机型/SoC/ART filter/构建类型；用“同档位+归一化+绝对值”双口径；合成数据标 `SYNTHETIC`。**结论：不是 block，是测量设计问题。**

### 2.3 V2 ArkTS 接口面：从 BLOCKED 改为“可做，但要先定义接口”

**你的假设**：调用代码可从开源网站获取或自己写，所需一切都能获取。

**重估**：

- 可以从开源 HarmonyOS/ArkTS 项目找 3 段真实 `protobufjs` 调用代码；找不到就自己写 3 段典型用法（decode、字段读取、JSON、`Object.keys`、`@Observed`、spread、`instanceof`）。
- 关键不是“有没有代码”，而是**“接口不变”指哪一级**：
  - API 级：签名/类型不变；值语义差异（JSON 形状、`Object.keys`、oneof 多成员）书面接受；
  - 值语义级：完全复刻 protobuf.js 7.6.5/8.x 的 observable 行为。
- ArkTS 语言限制（无 prototype、禁 `delete`/`Object.defineProperty`/动态索引/`in`）使**值语义级几乎不可实现**；API 级可实现。
- 因此重估结论：**按 API 级兼容立项；值语义差异列清单，由验收方书面确认。** 如果验收方坚持值语义完全零改动，项目仍不成立。

**剩余风险**：开源代码版本/用法不代表发榜方真实业务；`@Observed`/ArkUI 状态管理可能不兼容。**对策**：V2 先做 3 段代码审计 + 1 个最小 ArkUI 列表 demo；差异清单签字。**结论：不是资源 block，是“接口定义”决策。**

### 2.4 V3 构造地板：从 BLOCKED 改为“可做，3–5 天”

**你的假设**：所需一切都能获取。

**重估**：

- 不需要先写完整 C++ reader；用 protobuf.js 解一遍拿对象图，再用生成的 ArkTS 类重建同样对象图，10 万条 × 1 KB = 100 MB，测 alloc+assign+string+GC+tape_read。
- 这是**唯一能在不写 25–30 人日生成器之前证伪 700 ms 的实验**；3–5 天可做。
- 判定：95% 上界 >0.50 s → 700 ms 不可达，转 1.5×/P3；≤0.45 s → 值得投入 P4；0.45–0.50 → 有条件。
- 如果 A 臂（Long/默认值/oneof 兼容模式）因 ArkTS 语言限制写不出来，就测 B 臂（性能模式），并把“零改动”降级为 API 级。

**剩余风险**：构造地板可能 >0.50 s；这不是资源能解决的，是物理/语言约束。**对策**：先做 V3；不通过就缩范围，不写 P4 生成器。**结论：不是 block，是“先测再投”的决策门。**

### 2.5 V4 NAPI/P3：从 BLOCKED 改为“可做，2–3 天”

**你的假设**：所需一切都能获取或 AI 生成。

**重估**：

- 一个 NAPI `add(a,b)` + 一个 `napi_new_instance` 20 字段 + 一个逐字段 `set_property` 工程，AI 可生成骨架；上板测 10 万次，2–3 天。
- 关键：**P3-batch 可能比 P4 更简单更稳**。一次 NAPI + N 次构造，无 tape、无 materializer、无 external buffer；如果单对象构造 1–5 μs、V3 地板 <0.30 s，P3-batch 可能直接达标。
- 如果 P3-batch 不够，再考虑 P4-worker/sendable；最后才是 P4-row 双端生成器。

**剩余风险**：`napi_new_instance` 在 200 字段时可能很慢；NAPI 调试仍需人工。**对策**：先测 10/50/200 字段；用 break-even N 判定，不用 50–100 μs 的旧假设。**结论：不是 block，是“主线选择”实验。**

### 2.6 V5 Schema：从 BLOCKED 改为“可获得，1–2 周”

**你的假设**：所需一切都能获取或 AI 生成。

**重估**：

- 从开源项目/公开 schema 找 3–5 个热点 `.proto`，或自己写等价 schema；AI 可生成 WKT/optional/递归/Map 的测试用例。
- 关键：**现网 protobufjs 版本**（7.6.5 vs 8.x）必须锁；两者 oneof/默认值行为相反。
- WKT/Any、proto3 optional、未知字段、map<int64> 需要按“drop-in 用 protobuf.js / 跨语言 JSON 用 proto3 JSON”的权威基准做矩阵；不能一套通吃。
- `buf`/`protoc` 可安装；`buf breaking` 可以在 1 天内跑起来。

**剩余风险**：开源 schema 不代表发榜方真实业务；WKT/Any 可能让热点消息整条回退。**对策**：先做 schema 盘点 + top-3 命中率；热点含 Any/递归/editions 就缩范围。**结论：不是 block，是“schema 选择”问题。**

### 2.7 V6 安全：从 BLOCKED 改为“工具可获取，设备侧可做”

**你的假设**：板子后面买，其余能解决；`.so`/osv-scanner/syft/scancode/nm/readelf 应该可以获取。

**重估**：

- `nm`/`readelf` 随 binutils；`osv-scanner`/`syft`/`scancode` 可安装（Linux/WSL2/CI）；`.so` 由 NDK 构建。**这些确实可获得。**
- 设备侧 ASan 可能受 HAP/链接器限制；如果不可用，用 guard page + `-fstack-protector-strong` + `-D_FORTIFY_SOURCE=2` + RELRO/NX + 压力测试替代；**不能声称“零崩溃”，只能声称“有边界/有 fuzz/有压力测试”。**
- 三个“一小时证伪”仍要做：length-before-alloc、`napi_value` 缓存、external buffer transfer。
- 安全不是“买工具就过”，但工具可得后，风险从“无法验证”变成“工程验证”。

**剩余风险**：设备侧 ASan 不可用、恶意输入导致 DoS、finalizer/env teardown 难复现。**对策**：先做 host 参考模型 + 设备压力测试；把“零崩溃”改成“已知边界内不崩/超限拒绝”。**结论：不是 block，是“验证深度”问题。**

### 2.8 W0-L 法律：从 BLOCKED 改为“已授权，但保留书面记录”

**你的假设**：已经完全授权。

**重估**：

- 如果学校/俱乐部已书面授权，主体/IP/CLA 不再是 no-go；但仍需把授权文件、Apache-2.0 出站许可、贡献者许可归档，否则申报/开源时无法证明。
- 若“完全授权”是口头/内部授权，建议补一份一页纸的《知识产权与开源出站确认函》，由学校/俱乐部签字；这不是 block，是合规留痕。
- 专利 vs W2 公开：如果学校不打算申请专利，直接按 Apache-2.0 公开；如果打算申请，先申请再公开。

**结论：不是 block；从“法律 gate”改为“合规留痕”。**

### 2.9 W0-P 产品：从 BLOCKED 改为“不需要客户，按学校项目验收”

**你的假设**：不需要客户，只揭榜做大学生项目，学校有经费。

**重估**：

- 不需要商业 ROI、TCO、付费客户；这些从 Go/No-Go 中删除。
- 成功标准改为：**完成可复现的代码/生成器/基准/文档/Demo，通过课题验收，形成可展示的学生成果**；学校经费覆盖设备/差旅/耗材。
- 但仍要控制范围：1 个 App/3 个热点 schema/1 套基准，不要做“社区标准件/商业组件”。
- TCO 只作为“工作量/经费”参考，不作为“值不值得做”的 KPI。

**结论：不是 block；从“商业产品”改为“学生课题交付”。**

### 2.10 W0-A 架构：从 PARTIAL 改为“可做，先 P3-batch”

**你的假设**：所需一切都能获取或 AI 生成。

**重估**：

- 18-cell 矩阵、P3-batch、线程 A/B、streaming、row/vtable、Wasm 计划都已写完；缺的是 demo/实测。
- 资源到位后，先做 **P3-batch**（一次 NAPI + N 次构造、无 tape）；它代码量最小、部件最少、最容易验证。
- 如果 P3-batch 达标，砍 P4；如果不达标，再 P4-worker/sendable；最后 P4-row。
- 这样即使资源全部到位，也不会把 20 周押在“P4 唯一”的假设上。

**结论：不是 block；从“架构设计”进入“P3-batch 先行”的工程路线。**

## 3. 资源到位后仍存在的四个硬风险

### 3.1 ArkTS 值语义不可完全复刻（硬）

ArkTS 没有 prototype 概念，禁 `delete`/`Object.defineProperty`/动态索引/`in`，生成类字段必须初始化。protobuf.js 的 `Object.keys`/`JSON.stringify`/oneof 多成员/默认值行为无法 100% 复刻。

**处理**：按 **API 级兼容**立项；值语义差异列清单，验收方书面接受；不要承诺“业务零改动”到 JSON/Object.keys 级。若验收方坚持值语义完全一致，项目不成立。

### 3.2 700 ms 的物理地板（硬）

资源不改变“10 万条 × 10 对象 × 20 字段”的构造成本，也不改变 H（OH/Android 硬件差）。1.5× 是现实目标；700 ms 取决于：

- c（非 wire 占比）≤10–15%；
- tape_write/read ≤0.08–0.10 s；
- materializer 95% 上界 ≤0.45–0.50 s；
- wire 8–15×。

**处理**：V3 先测构造地板；不通过就 1.5×/P3，不写 P4 生成器。**700 ms 写成“目标”，不写“承诺”。**

### 3.3 20 周工期（硬，但可管理）

资源到位后，开发仍要 78–92 有效人日 + W0 2–4 周；17 周是 best case，20 周是 base。AI 能生成代码，但不能替代 NAPI 调试、真机性能调优、兼容性回归。

**处理**：按 20 周排；W0 2 周（平台/采购/工具链/schema）；W1–W16 开发；W17–W20 缓冲/验收。若必须 17 周，砍 encode 二期/场景数/ANI。

### 3.4 兼容/安全正确性（硬，但可用测试换信心）

- protobufjs 7.6.5 vs 8.x 行为不同；必须锁版本。
- oneof/default/WKT/optional/map<int64>/未知字段都有坑。
- 设备侧 ASan 可能不可用；不能承诺零崩溃。

**处理**：差分测试 + golden + fuzz + 边界表；把“零崩溃”改成“已知边界内不崩/超限拒绝”；兼容差异书面确认。

## 4. 重估后的推荐方案

### 4.1 定位

**“API 级兼容 + P3-batch 优先 + 热点消息 P4 + 20 周”的 student project**，不是“全量 P4 + 值语义零改动 + 17 周”的工业级重写。

### 4.2 路线

| 阶段 | 周期 | 工作 | Gate |
|---|---|---|---|
| W0 | 2 周 | 买板/借手机/装工具链；锁 API/ArkTS/protobufjs 版本；V2 接口定义；V3/V4 最小工程 | V0/V2 通过 |
| W1–W4 | 4 周 | P3-batch 最小实现 + 基准；V3 构造地板；G1 | P3-batch ≥3× 或绝对预算达标 |
| W5–W8 | 4 周 | 若 V3 过：P4 tape/materializer 最小实现；若不过：转 1.5× 路线 | G2 |
| W9–W12 | 4 周 | 兼容层/版本契约/WKT/optional；安全边界/fuzz；G3 | 1.5× demo + encode ≤1.0× |
| W13–W16 | 4 周 | 热点消息/宽消息/流式/P4 优化；G4 | 700 ms 目标 |
| W17–W20 | 4 周 | 文档/演示/验收/缓冲；G5 | 验收 |

### 4.3 必达 vs 目标 vs 不承诺

| 项 | 必达 | 目标 | 不承诺 |
|---|---|---|---|
| 兼容 | API 级签名/类型不变；差异清单签字 | 值语义尽量接近 | JSON/Object.keys 完全一致 |
| demo 1.5× | 是 | ≤1.35× | 4.29× |
| bulk 700 ms | 否（目标） | ≤0.75 s | 全场景 700 ms |
| encode | 语义等价/≤1.0× | ≤0.9× | 字节级一致 |
| schema 同步 | 源码集成一键生成 | 二进制分发 | 任意 schema 免 NDK |
| 平台 | API 18/NAPI 或 API 23 混合 | ANI（若强制） | 全 ANI 后端 |
| 安全 | 边界/fuzz/压力测试 | 设备 ASan | 零崩溃 |

## 6. 结论

1. **资源不是 block**：板、手机、工具链、schema、代码、数据、安全工具、授权、经费都可获得；W0 的 `BLOCKED` 应重分类为 `RESOURCE-GATED`。
2. **项目从“暂不投标”改为“有条件可投”**：约 **3.55/5（B-）**，不是 3.93，也不是 2.0。
3. **真正的硬风险是三个**：ArkTS 值语义、700 ms 物理地板、20 周工期；三者都可通过“API 级兼容 + P3-batch 优先 + 1.5× 必达/700 ms 目标 + 20 周”管理，但不能消除。
4. **推荐路线**：API 级兼容、P3-batch 先行、热点消息 P4、20 周；如果验收方要求值语义完全零改动或 17 周内完成，则回到“不投/改题”。
5. **下一步**：先做 14 天资源到位 + V0/V2/V3/V4/G1；G1 不过就缩范围，不写 P4 生成器。
