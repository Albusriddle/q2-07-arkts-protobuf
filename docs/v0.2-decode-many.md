# V0.2 批量解码：`decodeMany(Uint8Array)`

> **SNAPSHOT（V0.2）**：V0.3 已将 POD/类型改为生成；V0.4 已生成 decoder。当前见 `docs/v0.7-hardening.md` 和 `evidence/v0_7_hardening.json`；本文 HAP 数字为 V0.2 历史快照。

日期：2026-10-29 ｜ 分支：`feature/v0.2-decode-many` ｜ 基线：V0.1 `516ffdb`
范围：**单条 `q207.demo.UserBatch` 消息体**的批量解码；不包含 tape/P4、多帧 framing、完整 codegen、设备运行/性能。

## 0. 结论

`decodeMany(bytes: Uint8Array): DecodedBatch` 已编译进 HAP：
输入是**一条 `UserBatch`**（field 1 repeated `User`，无 `[u32 len]` 前缀），返回
`{ users: DecodedUser[] }`，对象形状与 norm-v1 / protobufjs 7.6.5 一致。

**claim level**：`host_decoder_verified(batch)` + `napi_shim_compiled_not_executed`；
`napi_executed=false`、`device_run=false`、`installable=false`。**不得声称批量已在设备运行。**

## 1. API 契约

```ts
interface DecodedBatch { users: DecodedUser[]; }
decodeMany(bytes: Uint8Array): DecodedBatch;
```

- 输入：**exactly one `q207.demo.UserBatch` body**；不是一张 data-card，也不是“多个长度前缀帧”。
- 返回：`{ users: [...] }`（不是裸数组），与 `norm::user_batch_json` / protobufjs 的 `UserBatch.toObject()` 对齐。
- 每项 `DecodedUser` 与 `decodeUser` 相同：`id` 十进制字符串、`profile: null|object`、`email?/phone?`、`level?`、`scores` last-wins。
- 空 batch → `{ users: [] }`。
- `0a00` → 一个全默认 User，不是零个。
- 单条 User 字节直接传给 `decodeMany` 会因 `UserBatch.users` 期望 length-delimited 而失败/不匹配；必须先包一层 `UserBatch`。

## 2. 上限与内存边界

| 限制 | NAPI profile |
|---|---:|
| 输入大小 | 64 MiB (`max_message_bytes`) |
| `max_batch_users` | 100,000 |
| `max_objects` | 1,000,000（含 batch 自身 + User + Profile + MapEntry，因此有效 User 数更低） |
| `max_fields` | 2,000,000 |
| `max_repeated_elements` | 100,000 |
| `strict_wire_type` / `utf8_strict` / `map_reject_dangerous` | 固定 true，不暴露给调用方 |

`0a00` 是 2 B 一个空 User；64 MiB 输入仍可能产生极多对象，所以 **`max_batch_users` 才是批量上限**，64 MiB 只是输入上限。
100,000 对象是**上限**，不是 UI 线程建议值；同步构造 100k 对象可能造成明显卡顿，后续批量/worker 化时应重新评估（V0.2 不测性能）。

## 3. NAPI 实现要点

- 复用 `ReadInput`：只接受 `Uint8Array`、`napi_get_typedarray_info`（`data` 已按 `byteOffset` 调整）、detached fail-closed、空输入合法、>64 MiB RangeError。
- `decode::user_batch` **先完整解码并检查 Code**；失败直接抛异常，**不构造/不返回部分数组**。
- 成功后用精确 `users.size()` 创建数组；外层数组/结果对象在 callback scope，**每个 User 一个 `napi_handle_scope`**，只包 `BuildUser` + `napi_set_element`，先 set 后 close；`ScopeGuard` 保证异常路径关闭。
- `decodeMany` 返回 `{ users }`；对象数组引用在 close 后由数组持有，不需要 `napi_escape_handle`。
- 所有 `napi_*` 失败抛错并 `return nullptr`；C++ 异常在顶层 try/catch 拦截，不穿越 C ABI。
- 错误映射：参数/非 Uint8Array/detached → `TypeError`；64 MiB/ObjectBudget/BatchTooLarge/FieldBudget → `RangeError`；其它 decode code → `Error`，带 `E_*` 与 batch body offset。

## 5. 已知限制

1. **未设备执行**：只证明 host decoder/object model、NAPI 编译/链接和 HAP 构建；handle scope/数组构造未在 ArkCompiler 上运行。
2. **未做多帧 framing**：bench data-card 的 `[u32 len]` 帧格式不是本 API 的输入；V0.2 一次只解一条 `UserBatch`。
3. **对象上限不是性能承诺**：100k 是安全上限；同步 100k 构造可能阻塞 UI，后续 P3/multi-worker 再优化。
4. **完整 codegen 仍未做**：字段表/wire type 已生成，POD/decoder/ArkTS 类型仍手写。
