# V0.8：native vs protobufjs host-only benchmark

日期：2026-10-30 ｜ 分支：`feature/v0.8-bench` ｜ 基线：`main` `def824f`

## 0. 结论

新增 S1/S3 数据卡的 protobufjs 7.6.5 baseline，并生成
`evidence/host/bench_compare.json`。

**结果必须先看清：host 上 native POD decode 并没有达到 1.5×，反而略慢于 protobufjs decode。**

| 数据集 | native decode median | protobufjs decode median | native/pbjs |
|---|---:|---:|---:|
| s1_user_1kb（8,178 msgs） | 13.23 ms | 9.06 ms | **0.68×** |
| s3_100mb（102,100 msgs） | 149.52 ms | 112.67 ms | **0.75×** |

这不是“揭榜指标已验证”；它说明当前 native host decoder 还不是性能答案。

## 1. 这次做了什么

- 新增 `src/host/ts/protobufjs_bench.mjs`：
  - 同一 `[u32 len][UserBatch]` 数据卡；
  - protobufjs `UserBatch.decode`；
  - 单独的 `decode + toObject({defaults:true,longs:String})`；
  - 3 次重复，median；
- 新增 `scripts/compare_protobufjs_bench.py`：native/protobufjs 对比；
- `build_host.sh` 新增 `protobufjs-bench`、`bench-compare` step；
- `collect_evidence.py` 纳入新 CSV/JSON。

## 2. 为什么不能把这个比例当成验收结论

- native 侧是 **C++ POD 构造**（vector/string/profile/map entry）；
- protobufjs 侧是 **JS object 构造**；
- host 编译器/Node/CPU 与目标 ArkCompiler/设备不同；
- 没有 NAPI `c_call/c_con`、RSS/GC、AOT；
- 目标要求是设备/API 级，host 比例只能作为“是否需要优化”的信号。

## 3. 解读

1. **S1 接近 1×，S3 明显落后**：更长的 100 MiB/100 帧路径暴露了 allocation/重复构造成本；
2. native 的 `map`/`profile`/`tags` 构造可能比 protobufjs 的 JS object 更重；
3. 若目标是 1.5×，当前 host 实现不够，必须：
   - 用 **arena/对象池** 降低分配；
   - 优化 generated decoder 的字段/vector 操作；
   - 把 decode 与 materialize 分开测；
   - 在设备上验证 NAPI/ArkTS 成本。
4. 纯 ArkTS 生成器、protoc-gen-napi、Turbo 官方方案仍需在同一 conformance/data card 上比较。

## 4. 验证

- normal host：**468 / 0 failed**
- ASan：**457 / 0 failed**
- fake NAPI：PASS
- `bench_compare.json`：HOST-ONLY；`not_claimed` 包含 device/1.5x/700ms
- HAP：沿用当前构建，不因 benchmark 变更重新声明设备结果

## 5. 下一步

1. 先做 **native decode 优化**（尤其 S3、map/profile/tags）；
2. 再做 protoc-gen-napi/官方方案同卡对比；
3. 有设备后测 NAPI/ArkTS 对象构造和 AOT；
4. 不能把 host 0.95×/0.73× 写成 1.5×。
